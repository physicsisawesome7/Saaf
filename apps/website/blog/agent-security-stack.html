The agent security stack is taking shape: sandboxes, policy engines and credential brokers

Lalit Shukla
9 Nov 2026 · Research note · 3 min read
AgentsSecurityInfrastructure

A year ago, agent security mostly meant writing careful system prompts. This autumn it started to look like infrastructure, with separate layers that each enforce one thing, outside the model.

From prompts to layers

Prompt injection is still unsolved, and nobody serious now expects the model to defend itself. The response is the one security engineering always reaches for: put hard boundaries around the thing you can't fully trust, and make each boundary simple enough to reason about. Two launches in October 2026 show the shape this is taking.

Sandboxes that know about actions

On 7 October, AWS released Strands Box in developer preview, an Apache-2.0 sandbox for agents, with a policy language called Dogwood. Its design has two layers. Containment uses the operating system's own isolation (the launch post cites macOS Seatbelt) as the hard boundary on files and network, deliberately without containers or virtual machines. Inside that boundary, policy decides which actions are allowed.

The interesting part is where policy is enforced: at a proxy that all outbound traffic must pass through, at the Python and shell interpreters the agent uses, and at a broker for MCP tool calls. Policies use Cedar-style permit and forbid rules and can depend on history, such as "at most three Slack posts in ten minutes". The gateway also swaps placeholder tokens for real secrets only on permitted requests, so the agent never holds the credential.

Credential brokers

On 22 October, 1Password launched 1Password for Agents, aimed at personal AI agents that sign in to websites. When an agent reaches a sign-in form, it identifies itself to 1Password with its own key. The person sees which credential is needed and why, and approves on their own device. 1Password then fills the credential straight into the form, so the agent never sees or stores it. The launch named a long list of agent and browser-automation partners.

Brokering matters because the most damaging thing an injected instruction can do is exfiltrate a secret. An agent that never holds a password can't leak it.

How the layers fit

  • Policy answers "is this action allowed, given what has happened so far?"
  • The sandbox makes sure there is no way around the policy: no direct network, no stray file access.
  • The credential broker keeps secrets out of the agent's context entirely.
  • Human approval covers what policy can't decide: irreversible, unusual or high-value actions.
  • The audit log records every decision, so the whole chain can be checked afterwards.

What's still missing

  • Data-level access control. Sandboxes govern actions, not what an agent may read in a knowledge base. An agent that searches with an all-seeing service account still leaks through its answers. Retrieval has to be filtered to the person asking, as we explain in Permission-aware retrieval.
  • Answer verification. None of these layers checks whether what the agent tells you is true. For answers people act on, each claim should be checked against its source. See Check every sentence.
  • Agent-to-agent trust. As agents call other agents, over MCP and similar protocols, each hop is another place for injected instructions to enter. Policies will need to follow the request across agents, not just within one.
  • Shared standards. Policy languages, sandbox protocols and approval flows are still product-specific. The foundations now hosting agent standards are the natural place to converge.

This is the layer Smriti works in: agents that act as the asker, answers verified against their sources, approval for writes after untrusted content, and an audit trail of every step. Sandboxes and brokers below, verified knowledge above: that's a stack worth trusting.
