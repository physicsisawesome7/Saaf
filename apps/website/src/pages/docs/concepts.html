How Smriti works

Every answer goes through the same pipeline, whether it comes from the web app, an agent, a workflow or a chat bot.

The path of a question

  1. Guard the input. The question is scanned for injection attempts, and personal data is masked with Saaf.
  2. Expand. Abbreviations and synonyms from the organisation's glossary widen the search.
  3. Search with the access filter. Hybrid keyword and vector search runs with the asker's permissions as a filter.
  4. Re-check access. Every result is checked again against the source of truth before it can be used.
  5. Apply version rules. Superseded text is dropped, and amendments in force on the date asked are attached to the clause they change.
  6. Rerank and write. The best passages are reranked. Totals over tables are computed in code. Otherwise a model writes an answer, or a verified extract is used.
  7. Verify. Each sentence is checked against the passages it cites.
  8. Answer or abstain. A failing answer is replaced by a verified extract, or Smriti says what is missing.
  9. Record. A trace of the run and an entry in the audit log.

Verification

An answer is split into sentences. Each factual sentence must cite passages. Its support is the share of its content words found in those passages, and every number, amount, percentage and clause id must appear verbatim in a cited passage. Uncited factual sentences count as unsupported. The score is shown with the answer and drives abstention.

Versions and amendments

Documents are linked by supersession and amendment relations. A question can carry an "as of" date. Retrieval returns the text in force on that date, and a clause always arrives together with every amendment that applies, so the answer leads with the amended text.

People, roles and grants

The person asking is a principal with roles. Roles give grants (view, upload, curate, administer, audit) and a scope: which divisions, projects, classifications and document types they may read, and which personal data they may see unmasked. An administrator configures the system without being a reader of its content.

Packs

An organisation is configured as layered packs. Platform defaults load first, then an optional vertical pack for an industry, then the tenant pack: models per task, roles, sources, document schemas, guardrails, glossary, skills and evaluation sets.

Skills

Skills are coded domain checks: an extractor, rules written in code, and an explanation. Thresholds are read from the document in force, never hard-coded, and results become drafts that go through maker-checker approval.

Evaluation and release gates

smriti eval gate runs a golden question set, a leakage suite that probes every person against every document they may not see, a red-team set, and the skills' planted-defect tests. CI blocks a release when any gate fails. Run the same gates on your own golden set.
