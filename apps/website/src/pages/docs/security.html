Security and access

Smriti assumes the model will sometimes be wrong or be fooled, and puts the guarantees in code around it.

Access control

  • Two enforcement points. A filter during search, then a bulk re-check against the source of truth before anything is used.
  • Administrators are not readers. Configuring the system doesn't grant access to its content.
  • Agents act as the asker. Agents, workflows, widgets and bots search only what the person behind them may see. An agent's sources narrow access, never widen it.
  • Leakage suite. Every person is probed against every document they may not see, in CI.

Personal data

Personal data is masked by category and role, using Saaf: before a model sees a question, document passage or tool result, and before anything is sent to an external tool. People who may see a value see it restored. The index holds masked text by default.

Prompt injection

  • Inputs are scored for injection, with an optional guard model for unsure cases.
  • Documents and tool results are treated as data, scanned and flagged.
  • After a run has read outside content (web, API, MCP, SQL), every action that changes data waits for human approval, whatever the agent's setting.

Actions and approvals

Agents ask before changing data by default. REST write operations are hidden until a curator allows them, and then always need approval. MCP tools not marked read-only need approval. Only the person who started a run can approve it.

Infrastructure

  • Credentials for sources, tools and bots are encrypted at rest and never returned by the API.
  • Egress guard on every outbound request, including redirects.
  • Code sandbox: no network, read-only root, non-root user, no capabilities, memory, process and time limits.
  • Downloads created by agents are always served as attachments, never rendered.
  • Integrations verify every inbound request: signing secrets, secret tokens, Ed25519 signatures or an origin allow-list.

Audit

Answers, tool calls, approvals, access decisions and configuration changes are written to a hash-chained log. Verify the chain with smriti audit-verify.

Deployment checklist

  1. Turn on token auth (SMRITI_AUTH=token) behind your SSO proxy.
  2. Serve over TLS through a reverse proxy.
  3. Set SMRITI_SECRET_KEY from your secrets manager, rather than relying on the key file Smriti creates in its data directory.
  4. Block private networks for crawlers if you don't crawl the intranet (SMRITI_EGRESS_ALLOW_PRIVATE=0).
  5. Use read-only database accounts for SQL sources and tools.
  6. Run the release gates on your own golden set before go-live.
