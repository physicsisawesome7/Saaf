An agent should never know more than the person asking

Lalit Shukla
2 Nov 2026 · Essay
AgentsAccess controlRAG

The fastest way to ship an internal AI assistant is to give it one account that can read everything. It is also the fastest way to make access control meaningless. Whoever can talk to the assistant can now read whatever the assistant can.

The service-account shortcut

Access control in most organisations is already carefully designed. The land officer can see owners' names; the site engineer sees the plot but not the owner; the vigilance team sees case files no one else does. Then an assistant arrives. It needs to search documents, so it gets a service account, and the service account needs to answer everyone's questions, so it gets read access to everything.

From that moment the assistant is a side door. It doesn't need a clever attack. The engineer just asks it who owns the plot. OWASP's list of the top risks for LLM applications names both halves of this: sensitive information disclosure, and excessive agency, where an assistant holds more permissions than its task needs.

Filtering the answer afterwards doesn't fix it. Once restricted text has reached the model, it can surface in a summary, a comparison or a number that no keyword filter catches.

One rule

The rule we build Smriti on is simple to state: an agent acts as the person asking, and never as the person who built it. In practice that means:

  • Retrieval is filtered to the asker first. The agent's own sources can only narrow what is searched, never widen it. An agent built by someone with wide access shows less to someone with less.
  • Tools carry their own role lists. Connecting a database or an API to an agent doesn't make it available to everyone who can chat with that agent.
  • Sharing a conversation shares no access. When someone opens a shared link, answers citing documents they can't open are withheld.
  • Keys never outrank their creator. An API key acts as the person who created it, for one agent only.

None of this depends on the model behaving. A model can't reveal a passage it was never given.

Every surface needs an identity

The rule gets harder the moment an agent leaves its own app. A widget on the intranet, a Slack bot or a Telegram bot for field staff all receive questions from people Smriti didn't authenticate. Each one has to answer the question as whom? explicitly, and we give three answers:

  • As its creator. Everyone sees what the creator can see and no more. That is right for a public help desk over public documents, and wrong for anything else.
  • As the signed-in user. The host site's own server signs a short-lived token for the person who is logged in, and the widget answers as them.
  • As a mapped person. An administrator maps chat-app accounts to people in the directory. Anyone unmapped is refused rather than given a default.

Approvals follow the same logic. When an agent wants to do something that changes data, the button to approve it works only for the person who asked. Someone else in the Slack channel can't press it for them.

When answers leave the building

A chat app is a third party that keeps a copy of every message. Two extra checks apply to answers sent there. Personal data in the reply is masked by default, with a note that it was hidden. And an answer citing documents above the integration's classification limit is replaced by a link back to Smriti, where the reader's own access decides what they see.

What it costs

Acting as the asker is not free. The same question can get different answers for different people, which surprises users who compare notes, so the interface says when results were limited. Caches have to be keyed by access, not just by question. Scheduled agents need an owner to act as. And a mapped bot needs someone to keep the mapping current.

We think those costs are worth paying. The alternative is an assistant that quietly undoes every access decision the organisation ever made.
